2

The five answers — this is the product spec

/ identical for both accounts

This is the closest thing to a requirements document in the whole brief. Each question has a weak version that reads like a generic CRM and a strong version that reads like someone who did the work. The third line is mine: what the screen has to do to make the strong answer true.

Q1

What is the book worth?

Money
Strong

Each deal at a value you can back, with the file or person behind it. What you cannot back is shown apart.

Weak

One big total, copied from what a champion said.

SCREEN →Three buckets, never one number: Backed (verified + qualified/agreed), Claimed (told to us, no file), Unknown (never heard of). Deal value only exists after qualified — the schema says so — so anything before that is labelled, not summed.
Q2

Who holds the power?

People
Strong

For each deal: who decides, who pays, who uses it, who could block it, and where each stands with you.

Weak

A list of contacts.

SCREEN →Four named roles per deal, each a person id + warmth (guarded · neutral · warm · ally) + "waiting on". Unfilled role is a gap, never filled by a guess. The account sheet already lists stakeholders you have never met — those are the Q5 answers.
Q3

What do you do first?

Action
Strong

The first three moves, ranked, each with an owner, a date and the deal it moves.

Weak

Follow up with the client.

SCREEN →Exactly three, ranked by a written score: deadline proximity × value × stage × blocker status. Owner must be a real Flytbase person id. Date must land inside the deal's deadline. Every move cites the deal id it advances.
Q4

What is about to go wrong?

Risk
Strong

Deadlines at risk, people going cold, deals that are stuck, and when each turns bad.

Weak

Everything marked green.

SCREEN →Four detectors, each with a date it turns bad, not a colour: deadline breach, warmth decay (no contact, or dropped a level), stage stall, and live signal. Red must be earned by a rule — never by vibes.
Q5

What do you still not know?

Gaps
Strong

The gaps your plan rests on, and who could fill each one.

Weak

No gaps, or guesses shown as facts.

SCREEN →Gaps are computed, not narrated: missing role, fact still at claim, deal with no owner, "never met" stakeholder, deadline with no offer. Each row names a person who could close it. "No gaps" is a scoring failure, not a win.

4

The rules that shape the build

/ not style advice — architecture

Do

  1. Use any tools you like, AI included.
  2. Fetch once and store it: each token gets one call a minute.
  3. Keep your token on a server, never in browser code.
  4. Expect your data to change while you build.
  5. Hand in early — you can change links until time is called.

Do not

  1. Show a number without its source.
  2. Invent an id, a fact or a person.
  3. Work with other players — this is solo.
  4. Leave the hand-in to the last minute.
The constraint that decides the architecture

One call per minute, writes included. That is roughly 800 calls for the whole build window — and the data arrives as nested per-account JSON with separate paperwork, feature requests, release notes, people and signals. So: one full ingest, everything persisted, and every screen a read of our own store. The MCP is a source, never a render path.

The corollary is the one teams get wrong: because we cannot re-fetch per page view, the store has to be versioned. Judges check numbers against "your morning" — so each ingest is a timestamped snapshot, and a citation says which snapshot it came from. When the payload changes mid-build (it will), we show a diff instead of silently rewriting history.

Two numbers worth checking on first pull

The morning debrief shows a book of $214,249, but the five deal values legible in the screenshot sum to $194,249 — a $20,000 gap, so one line is missing from my read or the total carries a deal I cannot see. That is exactly the kind of thing the CRM must resolve on ingest rather than paper over: if the total and the parts disagree, say so on screen.

The same debrief reports "best reply chosen 80% of the time" and lists four replies that would have worked better. That is a coaching dataset — the reason deals went cold. It belongs in Q3 and Q4, not in a footer.

8

What actually loses points

/ ordered by how quietly it kills you
×

Building the dashboard before reading the paperwork

The five answers are already latent in the files. If we design panels first, we invent structure and then fit evidence to it — which is the definition of the weak column.

×

One headline number

"Book: $214,249" is the weak answer even if it is correct. It has to arrive split into backed / claimed / unknown, with the ids showing.

×

Using up the minute on page loads

Any design where a route calls tools/call will stall within an hour and look broken in the judge's window.

×

Filling a missing role with a plausible name

The brief lists the people you have never met precisely so we do not guess who decides. An unfilled power role must render as a gap.

×

Treating "about to go wrong" as a colour

Amber/red with no date is the same as everything green. Each risk needs the day it turns bad and the rule that flagged it.

×

Leaving ingestion until after the UI

Signals arrive during the build. If the store is not append-only from day one, the first event forces a migration at 2am.

Handover checklist

Four things unblock everything. The first two are blocking — I cannot make a single call without them.

  • 01The token — the QUESTIONATHON_TOKEN from "Show my token". It goes into a local .env.local only, never into the repo or the client bundle.
  • 02Confirmation of the MCP address — https://questionathon.alhackerscollective.com/api/public/mcp, JSON-RPC, streamable HTTP.
  • 03Where it lives — Fly.io / Railway (persistent disk, in-process scheduler) unless you say otherwise.
  • 04Repo name + owner — public and no sign-in, since judges read it.

One real decision. The 1-call-per-minute rule kills serverless cron, so hosting is not cosmetic:

Recommended

Single VM · Next + SQLite + in-process scheduler

Fly.io or Railway · one deployable · ~15 min setup
  • One writer, so the token bucket is trivially correct
  • Persistent disk keeps snapshots across deploys
  • Cron runs every 60s with no platform limits
  • One more account to create than Vercel

Vercel + managed Postgres + external cron

Vercel · Neon · GitHub Action every minute
  • Fastest deploy and previews
  • Three moving parts for one queue
  • Hobby cron cannot run per-minute; needs an outside pinger
  • Cold starts make the bucket racy under load
